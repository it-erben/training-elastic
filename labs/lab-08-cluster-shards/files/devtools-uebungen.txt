# ============================================================
# ÜBUNG 3: filter vs. must - Scoring bei Transaktionen
# ============================================================
#
# Erst mit must (Query-Kontext) - berechnet einen Score:

GET demo-smarttransactions/_search
{
  "size": 3,
  "_source": ["id", "status", "basket_info.sum"],
  "query": {
    "bool": {
      "must": [
        { "term": { "status": "ok" } },
        { "range": { "basket_info.sum": { "gte": 5000 } } }
      ]
    }
  }
}

# Frage: Sieh dir _score der Treffer an - welchen Wert haben sie?
# Wann hast du zuletzt nach der "relevantesten Transaktion" gesucht?
#
# Jetzt dieselben Bedingungen mit filter (Filter-Kontext):

GET demo-smarttransactions/_search
{
  "size": 3,
  "_source": ["id", "status", "basket_info.sum"],
  "query": {
    "bool": {
      "filter": [
        { "term": { "status": "ok" } },
        { "range": { "basket_info.sum": { "gte": 5000 } } }
      ]
    }
  }
}

# Frage: Was steht jetzt in _score? Vergleiche hits.total mit der
# must-Variante - die Treffer sind identisch.
# Merke: filter berechnet keinen Score und ist cachebar. Für exakte
# Bedingungen (Status, Betrag, Zeitraum) ist filter fast immer
# richtig. Kibana/KQL macht das automatisch - aufpassen musst du
# beim Programmieren direkt gegen die API.
#
# Zusatz: Füge in beide Abfragen auf oberster Ebene
#   "profile": true,
# ein und vergleiche in der Antwort unter "profile" die
# Query-Typen und Zeiten.

# Frage: Wie groß ist der Unterschied zwischen
# demo-smarttransactions und demo-smarttransactions-optimized --
# bei identischen Daten und nur 200 Dokumenten?
#
# Jetzt die Mappings - scrolle durch beide Antworten und
# vergleiche die Menge der Felder:

GET demo-smarttransactions/_mapping?filter_path=**.properties

GET demo-smarttransactions-optimized/_mapping?filter_path=**.properties

# Merke: Das Original hat über 150 Felder, das optimierte gut 100.
